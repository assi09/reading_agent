# Reflection

I drew the lines between the tools by asking what each one is allowed to *change*. `search_arxiv` never touches the reading list. It is safe to call any number of times, and it is annotated read-only so a host can run it without asking for permission. `save_to_reading_list` is the only code path that writes, and it writes exactly one paper. I made it accept an ID rather than a full paper object, so the model can't make up a title or author list. That meant the Action tool has to verify the ID against arXiv, which is technically a lookup inside an action. I kept that check in the shared `arxiv_client` module instead of calling the Data tool, and added a small cache of papers from recent searches so the common "search, then save the second one" flow doesn't send a second request to arXiv. `build_reading_list` contains no arXiv or storage logic of its own. It calls the other two tools in sequence and only adds the policy that ties them together: over-fetch, skip duplicates, stop after *n* saves. Because of that, every failure in the orchestrator comes from a tool that is already tested on its own, and the error messages pass through unchanged.

Three tools fit this use case well. Each covers a distinct kind of user intent: "what's out there?", "keep this one", and "do it all for me". The agent rarely confused them once the descriptions stated their side effects plainly. In a real product, though, three would be too few. The next tools I would add are a `remove_from_reading_list` action, since right now only the UI's delete buttons can remove papers and the agent cannot, and a `get_paper_details` data tool for citation counts or related work (for example via Semantic Scholar), with the reading list kept as a resource. I would also move from a JSON file to SQLite, add a `tags` field so the orchestrator can group lists by topic, and run the server over Streamable HTTP so the same reading list could be shared between hosts such as Claude Desktop and this agent.
